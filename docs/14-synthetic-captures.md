# 14 — Synthetic captures and the T0 baseline

2,000 captures generated by `scripts/make-synthetic.py`, hash-split 70/20/10.
Every label is true **by construction**: the text is assembled from a chosen
date phrase, duration, verb and object, so we know the answer because we picked
the parts — not because anyone judged the finished sentence.

That distinction is the whole point. The three supplied `*-300` files were
template-generated with *judged* labels, and `13-generated-datasets.md` records
why that made them worthless as ground truth.

## What these numbers mean, and what they don't

| Metric | Trustworthy? | Why |
|---|---|---|
| **date accuracy** | **yes** | A grammar. Generating "kal" and checking we read "kal" is real coverage |
| **effort accuracy** | **yes** | Same — "2 ghante" either parses to 120 minutes or it doesn't |
| **span-verified rate** | **yes** | Offsets either resolve or they don't |
| **dependency recall** | mostly | The referent text is chosen; matching it back is a real test |
| **type accuracy** | **partly circular** | Generator and classifier share a notion of "imperative verb" |
| **type — unfamiliar verb** | **yes — the honest slice** | 40% of verbs are deliberately absent from our lexicon |
| category accuracy | **no** | Reported on the generated corpus instead, and even that is agreement rather than correctness |

**None of it tells us whether our notion of "type" matches how Ganesh actually
writes.** Only the 300 real captures test that.

## The T0 baseline (dev split)

This is what B3's model has to beat, by enough to justify the quota.

```
type accuracy            80.7%   n=415
type — unfamiliar verb   56.4%   n=163   ← the number that matters
date accuracy            97.9%   n=187
effort accuracy          91.8%   n=147
dependency recall        68.1%   n=69
span-verified rate      100.0%   n=406
```

Read `type — unfamiliar verb` as the real figure. The other 80.7% is inflated by
the 60% of rows whose verb our lexicon already knows.

## Where T0 fails, from the confusion matrix

```
task      → note       36    unfamiliar verb, short line, so it reads as a fragment
reminder  → abstained  12    no recognised verb and too long to call a note
reminder  → note        8    same
link      → task        3    a URL with a full sentence wrapped round it
```

Almost all of it is one failure: **an imperative we don't recognise.** That is
exactly the gap a model is for, and exactly the comparison B3 must make.

## Two bugs this exercise found

**1. The eval harness had the wrong clock.** `now` was defined as three separate
literals and one was `1_795_000_000` — **Wednesday 18 Nov 2026**, not Monday the
23rd. Date accuracy read 52.2%; with the correct constant it is 97.9%. The
parser was right the whole time and the harness was scoring it against the wrong
day. Now defined once, in `SyntheticLoader.now`.

A wrong clock in the harness is worse than a wrong parser: it makes correct code
look broken, and the obvious response is to "fix" the thing that isn't wrong.

**2. My generator produced an unlearnable label.** `task` rows could carry dates,
and `reminder` rows always did — so "clean the kitchen kal" was labelled `task`
in one row and `reminder` in another, at random. 51 of 212 tasks were scored
wrong against a label no reader could have produced either.

Fixed by making the distinction real: **a reminder is time-anchored** ("call
Priya kal subah 9 baje"), **a task merely has a deadline** ("clean the kitchen
kal"). Type accuracy went 66.5% → 80.7% — not because the classifier improved,
but because the question became answerable.

A label that is not identifiable from the input is a generator bug, not a model
failure. Worth remembering when B3's numbers look bad.

## Regenerating

```bash
python3 scripts/make-synthetic.py 2000
```

Seeded, so it reproduces exactly. Splits are a pure function of the id, so
adding rows never reshuffles existing ones.
